# Триггерная модель для трансграничных переводов

Сигнальный слой: когда выгодно переводить деньги в TJS, UZS, KGS, AMD, KZT.
Кейс Альфа-Банка, хакатон 02–07.09.2026.

## Быстрый старт

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m ml.leakage             # ворота: доказательство отсутствия утечки
.venv/bin/python -m pytest -c pytest.ini   # 46 тестов: честность, корректность, срез
.venv/bin/python -m ml.signals             # сигналы на произвольную дату среза
.venv/bin/python run_product_numbers.py    # продуктовые величины: размах, потолок, кучность, коридоры
.venv/bin/python run_experiment.py         # базовые модели против индикаторов ТЗ
.venv/bin/python run_boosting.py           # CatBoost, XGBoost + отбор признаков
.venv/bin/python run_two_models.py         # две модели под две метрики
.venv/bin/python -m research.train_only_eda            # EDA только на development
.venv/bin/python -m research.model_study                # purged walk-forward, h=5
.venv/bin/python -m research.horizon_audit              # все пять горизонтов
.venv/bin/python -m research.publication_timing_audit   # сценарий после публикации ЦБ
.venv/bin/python -m research.calendar_day_robustness    # календарные дни + forward-fill
.venv/bin/python -m research.statistical_audit          # 4-недельный block bootstrap
```

XGBoost на macOS требует OpenMP: `brew install libomp`.

## Главное про честность

Требование «не заглядывать в будущее» — дисквалифицирующее, поэтому оно обеспечено
структурно, а не дисциплиной:

* весь ряд режется по времени в единственном месте — `past_slice` в `ml/features.py`,
  так что признаки физически не получают доступа к будущему;
* `ml/leakage.py` портит будущее и требует побитового совпадения признаков в прошлом;
* та же проверка сначала доказывает, что **умеет** ловить утечку: в срез
  подставляется реальная ошибка, и проверка обязана её поймать — иначе её вердикт
  ничего не стоит;
* `ml/validation.py` делит выборку по календарной дате и вычищает обучающие строки,
  чья цель достаёт до тестового периода. **Запас считается в публикациях, а не
  в календарных днях:** горизонт задан в публикациях, ЦБ публикует курс по рабочим
  дням, и 20 публикаций занимают до 40 календарных дней — запас в днях оставил бы
  в обучении строки, чья цель лежит внутри теста. Сторож `assert_no_overlap`
  проверяет ту же величину, а не свою собственную арифметику;
* `ml/signals.py::signals_as_of(ряды, T)` считает сигналы на произвольную дату среза,
  физически обрезая ряды по T перед построением признаков — кейс называет это
  условием проверяемости;
* отбор признаков идёт только по данным до первого тестового года.

`run_experiment.py` и `run_boosting.py` не запускаются, если ворота не пройдены.

**Чистых признаков недостаточно.** Заглянуть вперёд можно и там, куда ворота не
смотрят, — в решениях, а не в матрице признаков. Два таких решения закрыты кодом:

* **рабочая точка.** Порог срабатывания нельзя брать квантилем по объединённым
  out-of-sample оценкам: он тогда знает распределение оценок на тесте.
  `ml/evaluate.py::train_cutoff` считает порог только по обучающим оценкам фолда —
  поэтому частоты срабатывания на тесте у моделей разные, а не подогнаны под правило;
* **выбор модели.** Взять лучшую из десяти конфигураций по её результату на тесте —
  то же самое уровнем выше. `ml/selection.py::select_model` фиксирует модель до
  теста, по внутренней валидации периода разработки; максимум по тесту печатается
  рядом с пометкой «результатом не является».

Ворота проверяют и сами себя: сначала в срез подставляется реальная ошибка и проверка
обязана её поймать, а отдельный тест доказывает, что две порчи будущего (масштаб
и перестановка) ловят **разные** классы утечек. Умножение будущего на константу
сохраняет знаки и ранги, поэтому признак, читающий только направление движения,
пережил бы такую порчу незамеченным.

`tests/test_leakage.py` падает, если порог начнёт браться с теста, если выбор модели
изменится от порчи тестового периода или если очистка вернётся к календарной арифметике.

## Исследование 04.09.2026: новый ключевой результат

История расширена до 2010 года, признаки — до 279 причинных колонок, а проверка
разделена на development до 2016, general validation 2017–2020, заранее заданный
режимный блок 2022–2023 и последовательный аудит 2024–2026. Все пороги каждого
тестового года вычисляются только по прошлому году; конец train очищается по
фактической дате достижения target.

**Сильнейшее решение зависит от времени отправки сигнала.** Банк России обычно
размещает установленный курс до 18:00 по Москве. Если продукт гарантированно
отправляет уведомление после этой публикации, следующий эффективный курс уже
публичен. Политика «следующий курс не хуже текущего + cooldown 3 календарных дня»
даёт на 2024–2026 future-only lift **1,94 / 1,93 / 1,96 / 1,98 / 1,90** для
h = 1/3/5/10/20 и 1,36–1,38 сигнала на коридор в неделю. Нижние границы
четырёхнедельного block-bootstrap: **1,79 / 1,75 / 1,77 / 1,78 / 1,70**.
На календарной сетке с causal forward-fill вывод сохраняется: lift
**1,62 / 1,83 / 1,91 / 1,92 / 1,94**.

Это не «предсказание h=1»: первый шаг уже известен. Поэтому сценарий изолирован
в `research/publication_timing_audit.py` и разрешён только после фактической
публикации. Если уведомление должно уходить раньше, его использовать нельзя.

**Без знания следующего курса** лучший диагностический h=5 anchor — положение в
90-дневном диапазоне плюс momentum 20/60 — даёт lift **1,406**, частоту **1,03**,
минимум по годам **1,227** и по валютам **1,249**. Но он найден при анализе
финального периода; честно выбранная по 2022–2023 смесь дала на финале лишь
**1,260**. В отчёте эти числа намеренно разделены на locked и post-hoc.

Сложные модели не стали основным источником выигрыша. Лучший CatBoost/ExtraTrees/
XGBoost помогал как малая добавка к anchor на 2022–2023, но переносился хуже.
ETS, SARIMA, GRU и прямая регрессия будущего минимума также проиграли простому
ценовому anchor. Результаты и исходные таблицы лежат в `results/research/`.

## Предыдущий baseline на короткой истории

**Метрику кейса максимизирует одна строка кода, а не модель.** Правило
`pct_range_90 >= 95` обгоняет все десять конфигураций по достижимой выгоде:
+63 бп, ДИ [+33; +94]. По lift кейса — 1,39 против 1,35 у обученной модели, но этот
lift держится на глобальном знаменателе: на базе, известной в момент решения, он
падает до **1,00**. Достижимую выгоду это не отменяет — она от знаменателя не
зависит вовсе, и именно она у нас главная величина. Правилу к тому же
не нужны ни отбор признаков, ни выбор модели, ни калибровка порога — то есть ни одно
из решений, которые можно случайно принять по тесту.

**И у этого максимума нет допустимого текста.** Сигнал срабатывает, когда валюта
получателя дороже, чем в 99 % дней квартала. Разрешённая кейсом формулировка
«выгоднее, чем в 85 % дней» для такого момента звучала бы как «хуже, чем в 99 %»
и перевода не мотивирует; единственный мотивирующий текст — утверждение о будущем,
а оно кейсом запрещено. **Для оптимума заданной метрики допустимого текста не
существует** — это свойство метрики, а не нашей неспособности её оптимизировать.

**Требование ТЗ целиком не выполняет ничто.** Порог lift ≥ 1,3 достижим, но всё, что
его даёт, срабатывает 0,6–0,8 сигнала на коридор в неделю — заметно реже
обязательной полосы 1–2 (правило `pct ≥ 95` — 0,60; модель A — 0,70;
правило `pct ≥ 90` — 0,80). Внутри полосы лучший результат — 1,26 у правила `pct ≥ 85`. Ниже полосы
оказываются и все четыре индикатора самого ТЗ (0,39–0,90).

**Основной индикатор ТЗ «моментум, падение три дня» приносит клиенту −21 бп, а не
+92 бп** — вся его положительная выгода приходит из уже случившегося падения, а вклад
в будущее отрицательный. Причина проверена отдельно: после падения три дня подряд
ожидание окупается (+8…+38 бп за три публикации на четырёх коридорах из пяти), то есть
индикатор находит содержательный момент и **указывает в противоположную сторону**.
Это результат о данных, он не зависит ни от одной модели.

**Модели поверх этого дают небольшой выигрыш на коротких горизонтах и большой на
длинных — но длинные продукту не нужны.** Конфигурация, зафиксированная до теста, даёт
на h = 5 +24 бп достижимой выгоды, ДИ [+3; +44], и положительна в 5 годах из 6. Прирост
к компаратору, назначенному заранее (основной индикатор ТЗ «моментум»), по горизонтам
1/3/5/10/20: +17 / +30 / +45 / +96 / +63 бп. Большие цифры справа наполовину сделаны
отрицательным знаменателем — на h = 10 и h = 20 все четыре индикатора ТЗ уходят
в минус, — а сам горизонт в 20 публикаций означает месяц ожидания, которого клиент,
привязанный к зарплате, не выдержит. Продуктовыми мы считаем h = 3–5.

Если вместо честного выбора брать лучшую конфигурацию по тесту, те же данные дают
на 22 / 18 / 19 / 25 / 85 бп больше: это цена выбора победителя по тесту, а не
свойство моделей.

**По клиентской метрике значимых результатов нет ни у одной политики.** Правильный
контрфакт для срабатываний внутри окна — «продолжать ждать», а не «перевести в день
зарплаты»: клиент, дошедший до третьего дня, этот выбор уже сделал. С ним сигнал даёт
**+133 бп, ДИ [−71; +401] на 53 окнах — направление верное, значимости нет**. Рамка
продукта от этого меняется с «угадай дно» на **«перестань ждать»**, но подтверждена
она пока только знаком, не интервалом.

Значимые интервалы в работе есть только на достижимой выгоде метрики кейса: правило
«верх диапазона» +63 бп [+33; +94], верхний бакет светофора +48 бп [+22; +75].

Подробности — в [docs/04-dve-metriki-dve-modeli.md](docs/04-dve-metriki-dve-modeli.md)
и [docs/03-rezultaty-modeley.md](docs/03-rezultaty-modeley.md).

## Структура

|---|---|

| `ml/data.py` | загрузка и валидация рядов |
| `ml/features.py` | 92 признака только по прошлому: циклический календарь (`sin/cos`) и one-hot валюты |
| `ml/calendar_ref.py` | календарь праздников и дат выплат |
| `ml/targets.py` | обе метрики заказчика + разложение выгоды на достижимую и нет |
| `ml/baselines.py` | четыре индикатора ТЗ + однострочное правило сравнения |
| `ml/selection.py` | отбор признаков и выбор модели без подглядывания в тест |
| `ml/validation.py` | walk-forward с очисткой |
| `ml/models.py` | логрегрессия, случайный лес, sklearn GBM, CatBoost, XGBoost |
| `ml/two_metrics.py` | метрика клиента: выгода против реального контрфакта |
| `ml/leakage.py` | доказательство отсутствия заглядывания в будущее |
| `ml/signals.py` | сигналы на произвольную дату среза (публичный API проверяемости) |
| `tests/` | 46 тестов: честность, корректность признаков и произвольный срез |
| `run_product_numbers.py` | продуктовые величины: размах, потолок, цена ожидания, коридоры, кучность |

| `run_encoding_experiment.py` | честное сравнение старой и новой кодировки календаря/валюты |

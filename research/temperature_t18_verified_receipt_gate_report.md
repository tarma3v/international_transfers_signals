# T18: переключение по фактическому receipt ЦБ

## Итог

T18 устраняет различие между исследовательским replay и продуктовым запросом.
Историческая ветка по-прежнему может сравнивать модели при явно указанном
календарном допущении 18:30, но production-style API и CLI больше не считают,
что новый курс ЦБ появился только потому, что часы показали 18:30.

До зарегистрированного события receipt вечерний запрос удерживает последнюю
доступную pre-receipt модель. После события он разрешает after-publication
модель и сдвигает все зависимые market-update строки не раньше фактического
receipt.

## Проверенный пример

Для 1 сентября 2026 года и горизонта `h=5`:

| Запрос | Переданное событие | Источник по всем 5 валютам | Результат |
|---|---|---|---|
| 18:45 | отсутствует | `post_window_market`, последнее наблюдение 17:29:59 | after-publication модель заблокирована |
| 18:45 | receipt 18:42 | `cbr_receipt`, source 18:42 | новый курс допустим |
| 19:15 | receipt 19:02 | `post_receipt_market`, source не раньше 19:02 | плановая строка 19:00 задержана до receipt |
| 18:45 | явный research replay | `cbr_receipt` с допущением 18:30 | допустимо только как ретроспективный сценарий |

Без receipt температуры `h=5` в 18:45 равны примерно 31,9–39,1. При
иллюстративном подтверждённом receipt 18:42 они меняются до 42,4–62,3, потому
что в модель теперь законно входит новый опубликованный курс. Это не оценка
реального события 1 сентября: исторический timestamp 18:42 выбран только для
проверки state machine.

## Почему это важно

Сама after-publication модель была причинной относительно условного среза, но
продуктовый роутер мог слишком рано сообщить пользователю, что использует новый
курс. Такой дефект не обязательно меняет ретроспективный lift, однако нарушает
`as_of`: в конкретный день курс мог прийти позже или ingestion мог задержаться.

T18 разделяет два понятия:

1. `valid_from` модели — когда все её входы действительно доступны;
2. плановое время исторического replay — исследовательское допущение, которое
   нельзя выдавать за наблюдавшийся факт.

Если receipt приходит позже планового market-update, например в 19:02 для
строки 19:00, строка становится доступна в 19:02. Её market candle уже завершён,
но опубликованный курс — второй обязательный вход, поэтому итоговый source time
равен не раньше 19:02.

## CLI

Без подтверждённого receipt:

```bash
python run_case_output.py \
  --as-of 2026-09-01T18:45:00+03:00 \
  --horizon 5
```

После события ingestion:

```bash
python run_case_output.py \
  --as-of 2026-09-01T18:45:00+03:00 \
  --verified-receipt-at 2026-09-01T18:42:00+03:00 \
  --horizon 5
```

Старый сценарий доступен только явно:

```bash
python run_case_output.py \
  --as-of 2026-09-01T18:45:00+03:00 \
  --historical-calendar-assumption \
  --horizon 5
```

Флаги verified receipt и calendar assumption взаимоисключающие.

## Что T18 не доказывает

- Исторические реальные моменты публикации/доставки всё ещё не собраны.
- Timestamp 18:42 в примере не объявляется фактическим timestamp ЦБ.
- Числа вероятности, expected bps и AP37 не переобучались.
- Новый holdout не появился, lift не улучшался.
- Курс ЦБ остаётся proxy, а не банковской исполнимой котировкой.

Поэтому T18 — улучшение причинности и готовности к онлайн-пилоту, а не новый
рекорд точности. Следующий содержательный шаг — сохранить реальные
`received_at` в prospective shadow log и сопоставить их с latency ingestion и
банковской quote.
